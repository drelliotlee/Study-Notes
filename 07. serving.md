# Serving
- taking an already trained model w frozen weights, users now call it for inference
- model servers: TrochServe, Triton Inference Server, vLLM, or simple FastAPI wrapper
- why its not simple:
	- latency - online (<2sec) vs offline (in batches overnight)
	- throughput - if 1000 requests/sec, how to batch, queue, load balance
	- cost - no GPUs sitting idle
	- reliability - how to handle crashes, updates 
- batch vs real-time
	- batch - load model on gpu, run, shutdown
	- real-time - model stays loaded on gpu
		- make sure gpu not idle / wasted cost
		- plan for how to scale up when surge
	- continuous batching
		- some requests in a batch produced their EOS token, others did not, in next forward pass, just replace those rows w new request. 
- Cold-starts
	- provision gpu (1-3 min)
	- model ssd → cpu (10-30 sec)
	- model cpu → gpu (2-4 min)
	- other runtime stuff, compile cuda kernels, etc 
- How to deal with slow cold-starts
	- keep instances warm → pay for idle costs
	- pre-warming = predict when traffic will spike
	- keep model cached on cloud ssd instead of cloud storage
	- snapshot everything but the weights (OS, pytorch, cuda)

# CPU vs GPU
- cpu better for serial operations
	- can switch order of instructions under the hood
	- can guess which if-else branch to take
	- l1, l2, and l3 caches to reduce memory latency
- gpu has no optimizations
	- in fact if code has if-else, it evaluates both and throws away results from one
- most important gpus
	- Nvidia
		- P100 → V100 → A100 = current gold standard for training since 2020
		- T4 (mostly for serving/inference)
		- H100 = luxury top of the line
		- B200 = next generation
	- AMD 
		- MI250 & MI300
		- ROCm isntead of CUDA requires different software engineering
	- Google
		- TPU v4 & v5
		- XLA instead of CUDA

# OOM errors
- caused by
	- other processes sharing gpu, cuda overhead etc
	- bugs
	- human error/miscalculation in memory requirements
- not caused by
	- surges in traffic
	- surges in prompt length
	- surgest in responses going on without EOS token
	- these are all capped, padded, and truncated to the same max memory requirement. cannot occur suddenly and unexpectedly.
- why theyre bad
	- they fail hard - no exiting from oom error gracefully. everything dies.
	- hard to reproduce
- ways to deal with / avoid oom
	- quantization: reduce weights from bf16 → int8 → int4
		- int8 usually produces a 1-2% performance drop
		- first and last layers are most sensitive to quantization, keep them at higher precision
	- paged attention: ???
	- model offloading: use some cpu memory as quasi-gpu memory
	- engineering discipline:
		- even with perfect memory req calculations, leave 10-15% safety margin for unknown overheads
		- monitor gpu memory and stop adding new requests when at 85% 
		- truncate/enforce lengths/batch sizes at multiple points in pipeline

# What makes Deployment hard - Distributed systems engineering
- how to handle traffic spikes or crashes (oom, hardware)
- how to route traffic / load balance
- keeping track of versions on which instances (canary testing, A/B testing)
- plans/mechanisms for rolling back 
- how to scale w higher traffic?
	- web servers are easier bc
		- stateless. kv cache for a users conversation must continue on same instance.
		- spin up instantly. gpu models take time to load
- queueing
	- how to timeout requests over 30sec (user prob gave up)
	- how to priortitize jobs
- observability
	- how many requests being served
	- latency
	- gpu memory utilization
	- log failures, ooms, errors
