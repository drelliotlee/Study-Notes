# Memory Requirements
- if model has 7B parameters of weights & biases
	- need 14gb for parameters themselves
	- need 14gb for gradients of each param 
	- need 14gb for momentum (exponentially smoothed moving avg of gradients)
	- need 14gb for variance (exponentially smothed avg of gradients squared)
	- activation of every neuron of every training example during forward pass
		- use gradient checkpointing - stop during intermediate layers and store activations so we can just recompute from checkpoints during backprop instead of storing everything

# LoRA
- ![441](./attachments/06.%20fine%20tuning-1775119688374.webp)
- reduces number of parameters by factor of 1/r
- only train A & B.
- r = 8 works well for most tasls, can go up to 16 or 32 if domain shift is larger, original paper found very small improvements after increasing r
- singular value decomposition is the pure math idea behind why this should be a good idea

# Activation Functions
- sigmoid/tanh - struggles with depth, keep multiplying by numbers <1 → vanishing gradient
- ReLU - strict slope of 1 fixes problem, but dead neurons now
- GeLU - relu except smoother around 0 for more stable convergence

# Versioning
- every time you fine tune, you need to keep track of
	- base model
	- dataset trained on
	- hyperparameters (learning rate, epochs, batch size)

# Rollout
- rolling out a new finely tuned model is hard because
	- output space of llms is unbounded → hard to write tests
	- how do you evaluate if a model is behaving correctly? not easy
		- held-out sets - not easily defined for llms
		- human evaluation - slow and expensive, but accurate
		- proxy metrics - very rough, but cheap and fast
			- 
- best practices
	- staged rollouts / canary - only send 1%... 5%... etc of traffic to new model
	- shadow mode - send user requests to both old and new model, log and evaluate new one later

# Training Costs
- Memory - 7B parameters =40-80gb memory + hours/days of time
- Data - collection of high quality data, human expertise, cleaning, validating, versioning

# Re-training
when do we do it?
- newer, better base models
- discover bugs, cases where models perform poorly → need to collect more/higher quality data around these cases
- data drift
