# Leakage
- Target Leakage
	- AKA using unfair features (X's which were caused by Y)
		- predicting if a patient has diabetes Y, based on whether they are prescribed insulin X
		- predicting if a student will fail Y, based on whether they attended summer school X
- Train-Test Leakage
	- AKA illegal data manipulations on X before splitting rows into train set & test set
		- scaling, missing val imputation, target mean encoding, outlier removal, imbalanced class adjustments
	- correct way: manipulate X's on train rows only, apply same transformations to test set (do not refit)

# Imbalanced Classes
- Undersampling/Oversampling (discard/duplicate rows until balanced)
- Heavier penalties for incorrect predictions on rare classes
- Stratify test-train split to have same proportion of rare class
- PR-AUC is best model evaluation metric for imbal

# Pre-processing
- Scaling/Normalization
	- make numerical columns mean 0 variance 1 to make regression-based methods work better
	- unnecessary for tree-based methods
- Imputation
	- in practice, people just use simple mean for numerical, simple mode for categorical
- Outlier removal
	- more than 1.5x IQRoutside the 25th and 75th percentile
	- more than 3 std dev outside the mean 
		- less preferred bc affected by outliers
- Feature engineering
	- Unnecessary for Tree-based methods
		- if-then based interactions
		- any monotonic transformations (ex. log(A), A²) ← trees only care about ordering, not scale 
	- Still necessary for Tree-based methods
		- ratios: (colA/colB)
		- non-linear combinations: A² - B

# Feature Selection
- SHAP values is most intellectually sound way to measure feature importance. used to be intractable. but TreeSHAP made it tractable, so basically dominant feature selection method now
	- only 2 real remaining reasons you could object to using it
		- in theory we need to avg over all rows w exact value matches. not enough rows to do that, so in practice we have to just force substitute exact values into 100 rows.
		- RFE slightly easier to explain to non-technical stakeholders
- Recursive feature elimination still used by slower adopting people
- Using a meta-tree outdated and flawed, known to bias towards high cardinality categories 
```
F = set of all features

for each explain_row in dataset:
    for each feature i:

        for each subset S of F\i:

            for each bg_row in background:
                pred_without_i = model.predict(bg_row, but cols S replaced w explain_row)
                pred_with_i    = model.predict(bg_row, but cols S+i replaced w explain_row)

            lift_from_adding_i_given_S = avg_[bg_rows](pred_with_i - pred_without_i)

            weight = (|S|! * (|F|-|S|-1)!) / |F|!

            SHAP(explain_row, feature i) += weight * lift_from_adding_i_given_S

SHAP(feature i) = avg_[explain_rows]( abs( SHAP(explain_row, feature i) ) )
```

# Precision vs Recall
- precision = of predicted  +, what % right?
	- use when FP costly / fine if bad guys no caught
	- ex. tax audits, spam filter
- recall = of actual +, what % caught?
	- use when FN costly / further investigation of FP acceptable
	- ex. bomb checks, cancer

# Evaluation
- regression → root MSE
- binary classif → ROC-AUC (tpr vs fpr)
- binary classif + imbal classes → Precision-Recall AUC (tpr vs precision)
	- why? if imbal → just overpredict neg → fpr looks artificially good
- multi classif
	- industry → f1 (intuitive, always [0,1]. con is based on hard labels)
	- kaggle → log-loss (based on prediction probs)

# Ensembling
- hard voting 
	- makes no sense for regression
- soft voting
	- just avg prediction probs / predicted regression values
- stacking
	- prediction values / prediction probs become new features for final meta-model
	- must use folds → base model trains on folds 1,..., n-1, predict value on fold n.
